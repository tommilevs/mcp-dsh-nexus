# DSH Control Bridge — спецификация, черновик 0.1

> **Статус реализации:** это проектная спецификация и целевая архитектура, а не перечень уже готовых функций. Реализованное подмножество перечислено в корневом README. Скриншоты, навигация по UI, чтение/изменение настроек и управление плагинами пока не предоставляются текущим Host-плагином.

## Цель

Создать локальный MCP-мост к DeepSeek Harness Desktop, которым могут пользоваться разные MCP-клиенты — Codex, Claude Code и другие совместимые приложения. Через него ИИ сможет работать с видимыми чатами DSH и выбранными в Harness моделями, а пользователь — наблюдать их работу. Тот же набор ограниченных MCP-инструментов должен быть доступен моделям, запущенным внутри DSH, включая Qwen3.8-27B.

Мост — отдельный открытый проект и стандартный MCP-сервер, а не функция только Codex. Это делегирование через MCP, не встроенный тип Codex-сабагента.

## Архитектура

1. **DSH Host plugin** использует поддерживаемые API Harness для состояния, каталога моделей, рабочих пространств и сессий. Desktop-профиль управляется самим Electron-приложением; установка и включение плагина выполняются через его Plugins UI.
2. **Общий MCP endpoint** монтируется Host-плагином отдельным маршрутом `/api/dsh-control-mcp/mcp` в штатный DSH `webServer`, который в Desktop уже слушает loopback. Основной режим — Streamable HTTP: несколько клиентов подключаются к одному экземпляру, но получают изолированные MCP-сессии и права. Для MCP-клиентов, умеющих только запускать локальные процессы, добавляется небольшой stdio-адаптер к тому же сервисному ядру.
3. **Desktop adapter** — узкое дополнение к DSH Desktop для скриншота и навигации. Захват вызывает `WebContents.capturePage()` из главного процесса через типизированный RPC и возвращает только байты изображения. Переход к сессии использует отдельное типизированное Host→Client событие, которое обработчик renderer переводит в `ctx.uiWorkspace.openSession(target)`. Сам объект окна, Electron IPC, shell и произвольный доступ к файлам плагину не выдаются.
4. **DSH как MCP-клиент** подключает тот же loopback endpoint через свой MCP-клиент. Так Qwen и другие модели в DSH могут вызывать разрешённые инструменты моста.

Главный endpoint доступен только через loopback DSH `webServer`. Если сервер DSH привязан к `0.0.0.0`, bridge должен отказаться регистрировать endpoint, пока пользователь явно не настроит защищённый удалённый доступ. Так как штатная browser-аутентификация DSH ожидает cookie, MCP-маршрут выполняет собственную bearer-аутентификацию и не считает `Origin` доказательством личности. Запросы без `Origin` разрешены только с действительным bearer-токеном; при наличии `Origin` разрешены только точные loopback-origin из настройки, а `Origin: null`, чужие origin и wildcard CORS запрещены. Проверяются loopback peer address и точный `Host`; `X-Forwarded-*` не используются как источник доверия. Сетевой доступ, если понадобится, проектируется отдельно с аутентификацией и TLS/туннелем; не открывать порт в LAN или Интернет без этого.

Каждый bearer-токен имеет отдельную идентичность, набор разрешений, список доступных сессий и возможность отзыва. Токены хранятся через DSH credential store в записи владельца `dsh-control-mcp`, выдаются/отзываются через пользовательский интерфейс настройки bridge и не кладутся в обычный plugin config, URL, аргументы процессов, ошибки или логи. MCP HTTP session ID связывается с идентичностью токена; при каждом запросе проверяются и токен, и разрешения. Сессии Harness, созданные bridge, привязываются к создавшему их клиенту; доступ к прочим сессиям требует отдельной явной выдачи. Для защиты credential store ограничено число одновременных проверок bearer-токена; также действуют индивидуальный и общий пределы запросов для аутентифицированных клиентов. Приём тел POST ограничен четырьмя одновременными чтениями на токен и шестнадцатью на весь плагин; незавершённое чтение прерывается через 30 секунд и при остановке плагина.

## Важное ограничение текущего Desktop

В установленном DSH Desktop 2.0.14 сейчас нет API захвата окна для обычных плагинов или универсального Host→Client события навигации. Host работает отдельно от Electron main process; его текущий Desktop API не содержит метода screenshot, а список событий, пересылаемых renderer, задаётся самим приложением. В Compatibility-режиме область интерфейса и верхняя панель могут быть отдельными `WebContentsView`, поэтому нельзя считать, что захват `BrowserWindow.webContents` автоматически даст полный экран приложения.

Поэтому одного обычного плагина недостаточно для настоящего скриншота и автоматического открытия сессии. Нужна небольшая поддерживаемая интеграция DSH Desktop: выбрать активный UI renderer и безопасно передать PNG через узкий RPC; добавить allowlisted событие навигации и его клиентский обработчик. Если это API нельзя добавить через официальный механизм расширения, подготовить минимальный upstream-патч для Desktop; не подменять его глобальным захватом рабочего стола, не выдавать плагину Electron main API и не переиспользовать событие с другой семантикой.

## MCP-инструменты

### Реализованное подмножество текущей версии

**Диагностика и обзор:**

- `dsh_status` — состояние Host и активного профиля без секретов.
- `dsh_list_models` — провайдеры и точные идентификаторы моделей.
- `dsh_list_workspaces` — доступные рабочие области.
- `dsh_list_sessions`, `dsh_read_session`, `dsh_follow_session` — список, ограниченная история и получение новых событий/результата.

**Видимые чаты:**

- `dsh_create_chat` — создать сессию с явно заданным workspace. Используется текущая модель DSH по умолчанию; выбор модели намеренно исключён, поскольку API сессий DSH меняет глобальную модель по умолчанию.
- `dsh_send_message`, `dsh_wait_run`, `dsh_cancel_run` — отправить задачу, дождаться ответа, отменить выполнение.

### Целевые функции, пока не реализованы

**Визуальный аудит:**

- `dsh_capture_screenshot` — по явному вызову получить изображение активной области DSH. Ответ должен содержать текст с временем/размером захвата и обычный MCP `ImageContent` с PNG. Не снимать остальные окна или мониторы.
- `dsh_open_chat` — показать созданную или выбранную сессию в интерфейсе пользователя.
- MCP-клиент и выбранная модель должны поддерживать изображения. Если клиент или модель не передаёт изображения дальше, мост сообщит об этом; наличие картинки в протоколе само по себе не добавляет модели vision.

Инструменты конфигурации и управления плагинами заложить во вторую фазу: чтение настроек, предложение изменения, затем отдельное применение с подтверждением пользователя. Первая версия не исполняет shell-команды, не читает произвольные файлы и не изменяет профиль молча.

## Использование моделями внутри DSH

Для DSH создаётся отдельный профиль доступа **helper**. По умолчанию Qwen может просматривать состояние и сессии, читать выбранную историю, получать скриншот и предлагать изменения. Запуск новых чатов или отправка сообщений другим моделям включается отдельным разрешением. Секрет helper-токена выдаётся MCP-клиенту DSH из credential store только на стороне Host и никогда не показывается модели. Изменение конфигурации и установка/удаление плагинов требуют явного подтверждения.

Чтобы исключить рекурсивную делегацию, сессия, созданная мостом, по умолчанию не получает инструменты делегации этому же мосту; для каждого вызова задаётся предел вложенности и времени. Владелец может настроить права главной DSH-сессии отдельно.

## Безопасность и приватность

- HTTP использует loopback-only DSH `webServer`, проверяет bearer-токен, peer address, `Host` и при наличии точный `Origin`; отсутствующий `Origin` допустим только для native-клиента с токеном. Тело ограничивается 64 KiB во время чтения потока, включая chunked-запросы, до передачи в MCP parser. CORS отключён, токены не попадают в логи.
- MCP-транспортные сессии изолированы по токену; разрешения и допуск к Harness-сессиям проверяются на каждом tool call (read-only, chat, screenshot, admin).
- Токены создаются и отзываются через DSH credential store и UI bridge; удалённый MCP-клиент никогда не может перечислить или прочитать секреты.
- Скриншот показывает содержимое, уже видимое в DSH, поэтому захват выполняется только по вызову инструмента, с ограничением размера и без фоновых снимков.
- Workspace-действия ограничены зарегистрированными путями DSH. В инструментах нет общего `read_file`, произвольного URL fetch или shell.
- Ответы истории и логи ограничены размером и очищаются от токенов/секретов.

## Этапы и критерии готовности

**Этап 1 — MCP мост и видимые чаты:** HTTP endpoint, stdio-адаптер, обзор сессий/моделей, создание видимого чата, отправка запроса, ожидание и отмена. Проверить подключение Codex, Claude Code и ещё одного независимого MCP-клиента.

**Этап 2 — Desktop UI и изображения:** добавить типизированную навигацию к сессии и Desktop capture adapter; проверить переход к видимому чату, что PNG доходит как MCP image block и читается vision-моделью в Codex/Claude Code. Подключить endpoint из DSH и проверить Qwen3.8-27B на диагностике и аудите интерфейса. Отдельно проверить защиту от рекурсии.

**Этап 3 — управляемые изменения:** чтение и предложение изменений DSH-настроек/плагинов; применение только отдельным подтверждённым вызовом. Сохранить журнал изменений и понятный откат.

Готовность подтверждается тестами прав доступа, DNS-rebinding защитой (`Host`/peer), запретом чужих `Origin`, отсутствующим `Origin` с/без токена, отсутствием токенов в логах, изоляцией параллельных MCP-клиентов и доступных им Harness-сессий, корректным завершением/отменой, показом созданного чата в DSH и проверкой изображения в каждом заявленном клиенте. Совместимость изображения отмечается для конкретной пары «клиент + модель», а не обещается для всех клиентов автоматически.
